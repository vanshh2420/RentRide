1. INTRODUCTION

1.1 Purpose

This Software Requirements Specification (SRS) document details the complete functional and non-functional requirements for the RentRide Multi-Vendor Vehicle Rental Marketplace. It establishes a formal, verifiable contract between system stakeholders—including software engineers, platform architects, academic project evaluators, and prospective marketplace operators. The document specifies system behavior, constraints, algorithmic logic, interface designs, and operational data flows.

1.2 Scope of the System

RentRide is an enterprise-ready, cloud-native web platform that coordinates short-term vehicle rentals across two-wheelers (scooters, commuter motorcycles, electric vehicles) and four-wheelers (hatchbacks, sedans, SUVs). The software orchestrates customer discovery, real-time collision-free availability checking, tiered rental plans, digital payments, vendor fleet administration, offline walk-in bookings, physical trip custody (odometer/OTP), and machine learning services for recommendations, demand forecasting, and dynamic pricing.

  • Academic Evaluation Committee & Project Guides: Focus on Sections 1 to 6 (System Architecture, Requirements, Use Cases) and Section 11 (Business & Scheduling Logic).
  • Full-Stack Software Developers: Review Sections 3 (Functional Requirements), 8 (Data Dictionary), 9 (API Specifications), and 14 (Error Handling).

  • Data & Machine Learning Engineers: Refer to Section 12 (AI/ML Microservice Specification).

1.4 Product Overview & High-Level Philosophy

RentRide bridges the gap between independent vehicle owners and urban commuters. Built on a resilient three-tier architecture (React SPA, Express API, MongoDB) augmented by a Python FastAPI ML microservice, the platform enforces atomic data consistency, transparent server-side pricing, and verified digital trip handovers.

2. OVERALL DESCRIPTION

2.1 Product Perspective

RentRide operates as a sovereign, self-contained multi-vendor marketplace. It interfaces with external services strictly via authenticated HTTPS protocols (Cloudinary for media asset hosting, Razorpay for payment order capture, and internal microservice communication to FastAPI for ML inference). The system is completely cloud-agnostic, capable of local deployment via Node.js/Vite or distributed cloud containerization.

2.2 Product Functions Summary

  • User Identity & Access: Registration, login, profile management, driving license upload, role assignment (CUSTOMER, VENDOR, ADMIN).
  • Marketplace Exploration: City hub selection (Indore, Bhopal, Gwalior), multi-tier taxonomy filtering, dynamic fuel cost estimation.
  • Availability & Collision Engine: Deterministic interval overlap conflict prevention across digital bookings, offline walk-ins, and maintenance downtime.
  • Rental Duration Flexibility: Custom Hourly plans (1–24h), 12-Hour Day Passes, and 24-Hour Multi-day packages.
  • Checkout & Inventory Lock: 10-minute temporary inventory reservation lock (lockExpiresAt).
  • Payment Reconciliation: Razorpay order creation, payment capture, and HMAC-SHA256 verification.
  • Vendor Operations: Fleet listing, Cloudinary photo uploads, walk-in offline bookings, digital trip handovers (odometer/OTP), and return processing.
  • Platform Governance: Administrative vehicle moderation, user auditing, coupon lifecycle management, and global booking ledgers.
  • AI Microservice: Multi-attribute recommendation scoring, 7-day demand forecasting, and elasticity-bounded dynamic pricing.

2.3 User Classes and Characteristics

User Class Characteristics & Technical Profile Permissions & Capabilities
Public Guest Unauthenticated visitor browsing the platform via mobile or desktop web browser. View landing page, search and filter available vehicles, inspect vehicle details, calculate estimated fuel costs, simulate fare breakdown.
Customer Registered commuter or traveler requiring on-demand vehicle rental services. All Guest capabilities + create online bookings, apply coupons, execute Razorpay checkout, manage reservations, cancel trips, write verified reviews, receive in-app notifications.
Vendor Commercial fleet agency, bike rental shop, or vehicle owner listing fleet inventory. Manage vendor business profile, create vehicle listings (manual or 1-click catalog auto-fill), log offline walk-in bookings, execute vehicle handover/return workflows, schedule maintenance blackouts, view earnings metrics.
Admin System administrator responsible for platform governance and compliance. Platform-wide superuser: approve/reject vendor vehicle listings, review user KYC status, create and deactivate promotional coupons, inspect global financial transactions, view analytics.

2.4 Operating Environment

  • Client Environment: Modern standards-compliant web browsers (Google Chrome 110+, Mozilla Firefox 110+, Apple Safari 16+, Microsoft Edge 110+). Responsive on mobile (360px+), tablet, and desktop viewports.
  • Server Runtime: Node.js version 18.x or 20.x LTS running on Linux/Windows/macOS.
  • Database Environment: MongoDB version 6.0+ (MongoDB Atlas cloud cluster or local replica set).
  • AI Microservice Runtime: Python 3.10+ with FastAPI, Uvicorn, Scikit-learn, Pandas, and NumPy.
  • External Network APIs: Outbound HTTPS connectivity to api.razorpay.com and api.cloudinary.com.

2.5 Design and Implementation Constraints

  • Stateless Authentication: All backend endpoints rely on stateless JWT tokens; no session state is maintained in server memory.
  • Mathematical Collision Consistency: Availability queries must execute compound range checks ($lt / $gt) with strict exclusion of expired locks.
  • Deterministic Pricing Bounds: Dynamic pricing multipliers must never fall below 0.90x or exceed 1.35x.
  • Zero Binary Storage: The database stores no raw binary image data; all images are hosted on Cloudinary CDN and referenced by HTTPS URL and public ID.

2.6 Assumptions and Dependencies

  • Customers possess an active Indian mobile number, driving license, and access to UPI or online banking via Razorpay.
  • Vendors are legally authorized to lease vehicles commercially within operational jurisdictions.
  • Network latency between Express backend and FastAPI microservice remains under 150ms over internal HTTP.

6.2 Detailed Use Case Specifications (UC-01 to UC-17)

UC-01: User Registration

  • Actor: Public Guest / Customer / Vendor
  • Preconditions: User provides unassigned email address.
  • Main Flow: User submits name, email, password, phone, and role. System validates fields via Zod, hashes password via Bcrypt (10 rounds), persists User document, generates JWT, and returns authenticated session.
  • Alternative Flow: Email already exists → System responds with HTTP 400 Bad Request.
  • Postconditions: User record is active in MongoDB.

UC-02: User Login

  • Actor: Customer / Vendor / Admin
  • Main Flow: User submits email and password. System queries user including password hash, verifies password via bcrypt.compare, issues signed JWT, and returns role-specific profile.
  • Exception Flow: Invalid credentials → System returns HTTP 401 Unauthorized.

UC-03: Search & Filter Vehicles

  • Actor: Customer / Guest
  • Main Flow: User selects city hub (Indore, Bhopal, Gwalior) and optional filters (category, price, fuel, transmission, seating). System queries approved, active vehicles matching criteria and returns vehicle cards with pricing and ratings.

UC-04: Check Vehicle Availability

  • Actor: Customer / System
  • Main Flow: Customer selects vehicle, rental plan, duration, and start timestamp. System executes mathematical interval overlap check. If no overlapping bookings or maintenance intervals exist, system returns available status with exact authoritative price quote.
  • Alternative Flow: Overlap detected → System returns unavailable status with conflicting window notice.

UC-05: Create Online Booking & 10-Minute Lock

  • Actor: Customer
  • Preconditions: Vehicle is available for requested interval; customer is authenticated.
  • Main Flow: Customer confirms schedule. System creates Booking with status PENDING_PAYMENT, computes server-side price breakdown, and assigns lockExpiresAt = Date.now() + 10 minutes. Vehicle is locked from concurrent reservations.

UC-06: Make Payment (Razorpay Checkout)

  • Actor: Customer / Payment Gateway
  • Main Flow: Customer invokes Razorpay modal for locked booking. Upon successful transaction, client returns razorpay_order_id, razorpay_payment_id, and razorpay_signature. Backend verifies HMAC-SHA256 signature, transitions booking status to CONFIRMED, and creates audited Payment record.
  • Exception Flow: Signature mismatch → Payment marked FAILED, booking remains unconfirmed.

UC-07: Cancel Booking

  • Actor: Customer / Vendor / Admin
  • Main Flow: Customer requests cancellation on confirmed booking. System verifies cancellation policy, computes refund amount and cancellation fee, transitions status to CANCELLED, and releases inventory slot.

UC-08: Vendor Adds Vehicle

  • Actor: Vendor
  • Main Flow: Vendor submits vehicle specifications, tiered pricing (hourly, 12h, 24h), and photographs. System uploads images to Cloudinary, sets isApproved = true (or pending moderation), and saves vehicle record.

UC-09: Vendor Logs Walk-In Offline Booking

  • Actor: Vendor
  • Main Flow: Vendor inputs walk-in customer details (name, phone, license) and dates. System runs collision check and saves Booking with bookingType = OFFLINE, instantly blocking online marketplace availability.

UC-10: Vehicle Handover (Start Trip)

  • Actor: Vendor
  • Main Flow: Customer arrives at pickup hub. Vendor records starting odometer reading and fuel level. System transitions booking status from CONFIRMED to ACTIVE.

UC-11: Vehicle Return (Complete Trip)

  • Actor: Vendor
  • Main Flow: Customer returns vehicle. Vendor inputs return odometer reading. System computes extra km driven against daily cap, adds extra km fee if applicable, releases security deposit, and marks booking COMPLETED.

UC-12: Schedule Maintenance

  • Actor: Vendor
  • Main Flow: Vendor inputs service window (routine, repair, inspection). System verifies no confirmed bookings conflict with the window, creates Maintenance record, and blocks marketplace availability.

UC-13: Admin Approves/Rejects Vehicle

  • Actor: Admin
  • Main Flow: Admin inspects submitted vendor vehicle listing and clicks Approve or Reject. System updates isApproved flag, making vehicle visible or hidden in public marketplace.

UC-14: Submit Verified Review

  • Actor: Customer
  • Preconditions: Booking status is COMPLETED; customer has not already reviewed this booking.
  • Main Flow: Customer submits star rating (1-5) and comment. System saves Review, triggers Mongoose post-save hook, and recalculates vehicle's ratingAverage and ratingCount.

UC-15: AI Vehicle Recommendation

  • Actor: Customer / AI Microservice
  • Main Flow: System passes customer preferences to FastAPI /recommendations. Microservice evaluates candidate fleet via multi-attribute scoring, returns ranked recommendations with percentage match scores (60%–99%).

UC-16: AI 7-Day Demand Forecasting

  • Actor: Vendor / Admin / AI Microservice
  • Main Flow: Vendor views demand forecast for city hub. Microservice analyzes day-of-week seasonality, city multipliers, and fleet utilization, outputting a 7-day demand index curve.

UC-17: AI Dynamic Pricing Multiplier

  • Actor: System / AI Microservice
  • Main Flow: Pricing engine requests dynamic rate multiplier for vehicle booking date. Microservice applies day-of-week deltas, fleet scarcity thresholds, and city factors, returning multiplier bounded in [0.90, 1.35].

7.1 Entity Cardinalities & Multiplicity Rules

  • User (Vendor) to Vehicle: One-to-Many (1 : N). A vendor owns multiple vehicles; each vehicle has exactly one vendor owner.
  • Category to Vehicle: One-to-Many (1 : N). A category classifies many vehicles; each vehicle references one category.
  • Vehicle to Booking: One-to-Many (1 : N). A vehicle is associated with multiple historical and upcoming bookings.
  • Customer to Booking: One-to-Many (1 : N). A customer creates multiple bookings across their account lifecycle.
  • Booking to Payment: One-to-One (1 : 1). Each online booking references exactly one authoritative payment transaction.
  • Booking to Review: Zero-to-One (0 : 1). A completed booking produces at most one verified customer review.
  • Vehicle to Maintenance: One-to-Many (1 : N). A vehicle undergoes multiple scheduled maintenance events.

10. SECURITY REQUIREMENTS & IMPLEMENTATION

Security is enforced across the presentation, network, application, and data layers:

10.1 Authentication & Token Architecture

  • JWT Algorithm: HMAC-SHA256 signing using a 256-bit environment secret (JWT_SECRET). Tokens carry subject id and claim role.
  • Token Expiration: Default 24-hour lifetime, preventing indefinite session exposure.
  • HttpOnly Cookie Storage: Tokens can be transmitted via Authorization: Bearer <token> header or partitioned HttpOnly cookies to mitigate XSS exposure.

10.2 Cryptographic Password Protection

Passwords undergo one-way adaptive salting and hashing via bcryptjs with a work factor of 10. Cleartext passwords are never logged, transmitted in error traces, or stored in database backups.

10.3 Web Application Firewalls & Middlewares

  • Helmet: Sets HTTP response headers (X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Strict-Transport-Security).
  • CORS: Whitelists explicit origin origins matching CLIENT_URL with credentials support.
  • Rate Limiting: Enforces express-rate-limit restricting client IPs to 100 requests per 15-minute window.
  • Zod Input Sanitization: Request payloads undergo strict validation against Zod schemas; unexpected fields are automatically stripped.

11. BOOKING & BUSINESS LOGIC SPECIFICATION

11.1 Mathematical Interval Overlap Collision Prevention

RentRide enforces deterministic interval mathematics to prevent double-booking. For any candidate booking request with requested interval [Startreq, Endreq] and existing vehicle interval [Startexist, Endexist], a collision occurs if and only if:

Collision ⇔ (Startreq < Endexist) ∧ (Endreq > Startexist)

The database executes this check atomically using compound indexes: 

const conflictingBooking = await Booking.findOne({
  vehicleId,
  status: { $in: ['CONFIRMED', 'ACTIVE', 'PENDING_PAYMENT'] },
  startDateTime: { $lt: requestedEnd },
  endDateTime: { $gt: requestedStart },
  $or: [
    { status: { $in: ['CONFIRMED', 'ACTIVE'] } },
    { status: 'PENDING_PAYMENT', lockExpiresAt: { $gt: new Date() } }
  ]
});

11.2 10-Minute Temporary Reservation Lock

When a customer clicks "Reserve Vehicle", the booking is created with status PENDING_PAYMENT and lockExpiresAt = Date.now() + 10m. During these 10 minutes, no other user can book the vehicle. If payment succeeds, status updates to CONFIRMED. If the customer abandons checkout, queries automatically ignore the lock once lockExpiresAt < Date.now().

11.4 Pricing Formulation

The server computes transparent pricing breakdowns using exact formulas:

Base Price = HourlyRate × DurationHours (or Rate12Hour / Rate24Hour for fixed plans)
Surge Adjusted = round( Base Price × SurgeMultiplier ) [Surge = 1.15 on Fri/Sat/Sun]
Subtotal = max( 0, Surge Adjusted − CouponDiscount )
Platform Fee = round( 0.05 × Subtotal )
GST = round( 0.18 × Subtotal )
Total Payable = Subtotal + Platform Fee + GST + Security Deposit
Vendor Payout = Subtotal × (1 − CommissionRate) [Default Commission = 10%]

12. AI / ML MICROSERVICE DETAILED SPECIFICATION

The AI subsystem is deployed as an asynchronous Python/FastAPI microservice. It provides three core services:

12.1 Recommendation Scoring Engine

Computes multi-attribute match scores between vehicle vectors and customer preference vectors:

  • Category Match: +25 points for exact category slug match.
  • Budget Compatibility: +20 points if hourly rate ≤ maxBudget; penalty proportional to excess ratio if above.
  • Passenger Capacity: +15 points if seating capacity ≥ requested passengers (−10 if less).
  • Engine & Transmission: +10 points for matching fuel type; +10 points for matching transmission.
  • Rating Boost: Scaled boost: (ratingAverage − 3.0) × 6.0.
  • Output: Normalized score bounded between 60% and 99% with human-readable recommendation highlights.

12.2 7-Day Demand Forecaster

Analyzes day-of-week seasonality, city multipliers, and fleet utilization pressure:

12.3 Dynamic Pricing Engine

Computes dynamic rate multipliers bounded between 0.90x and 1.35x:

Dynamic Multiplier = clamp( 0.90, 1.35, BaseMultiplier + DayDelta + ScarcityDelta + CityDelta )
  • Saturday: +0.15 | Friday/Sunday: +0.10 | Tuesday/Wednesday: −0.05
  • Fleet Utilization ≥ 80%: +0.15 | ≥ 65%: +0.08 | < 35%: −0.05
  • City Multipliers: Indore (+0.05), Bhopal (+0.03), Gwalior (+0.02)

17. SYSTEM LIMITATIONS & KNOWN CONSTRAINTS

In accordance with academic rigor, current system limitations are explicitly documented:

  1. Automated Razorpay Refund API Trigger: While cancellation fees and refund amounts are computed and saved in cancellationDetails, live API dispatch to razorpay.payments.refund() is not yet executed automatically.
  2. Customer KYC Verification UI: Driving license fields are stored and displayed, but admin verification action buttons currently operate as a status viewer.
  3. Email and SMS Dispatch: Transactional vouchers are generated in-app; SMTP (Nodemailer) and SMS gateway (Twilio) dispatch are not configured in the active build.
  4. Interactive Map UI: Geographic coordinates ({ lat, lng }) are stored for pickup hubs, but interactive Leaflet map pins are not yet mounted on the Explore page.
  5. Expired Lock Cron Worker: Expired locks are excluded in availability queries, but background cron worker to transition status from PENDING_PAYMENT to EXPIRED is pending implementation.
